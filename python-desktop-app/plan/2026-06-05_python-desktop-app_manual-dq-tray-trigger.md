# Manual DQ Tray Trigger (Testing)\n\n## Problem\nDescription-quality popup nudges are not observable during testing windows, and both `description_quality_notifications` and `description_quality_nudge_preferences` remain empty in production validation. QA currently has no deterministic way to trigger a desktop-side nudge poll from the tray UI.\n\n## Root Cause / Context\n- The desktop poller starts lazily after login and logs only once on thread startup.\n- Poll cycles run in the background at adaptive intervals and do not emit INFO logs for each empty cycle.\n- There is no manual action in the tray menu to force an immediate poll and popup path check.\n\n## Proposed Solution\n1. Add a new tray item (near "View All App Rules...") for manual testing: trigger a one-off description-quality poll immediately.\n2. Implement a dedicated handler that:\n   - ensures the DQ poller exists (starts it if needed),\n   - optionally refreshes DQ popup preferences,\n   - performs a single `poll_once()` in a background thread,\n   - dispatches returned nudges via existing `_handle_dq_nudges`,\n   - logs clear outcomes (triggered, found N nudges, none found, errors).\n3. Keep existing scheduled/background behavior unchanged.\n\n## Acceptance Criteria\n1. When user is logged in and tracking is active, tray menu shows a clickable manual DQ test action.\n2. Invoking the manual DQ action performs a one-off poll without waiting for the normal poll interval.\n3. If nudges are returned, existing popup flow is used (`_handle_dq_nudges`).\n4. If no nudges are returned, app logs a clear "no pending nudges" message (and may show a non-blocking toast).\n5. Existing tray items (including "View All App Rules...") remain present and unchanged in behavior.\n\n## Out of Scope\n- Changing server-side scheduler cadence or Forge trigger definitions.\n- Modifying AI scoring rules or notification insertion SQL logic.\n- Reworking DQ poller interval strategy.\n
